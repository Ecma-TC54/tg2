  - Standards submission and formatting

  - Documentation management and style guide

  - PURL use case context

    - The team plans to introduce a new independent go PURL type to replace the legacy implementation.
- **ECMA updates:** Michael Herzog reported that all formatting issues for the two standards being submitted for December, ECMA-427 2nd Edition and ECMA-xxx-VERS 1st Edition, have been resolved. Michael Herzog noted a remaining bug in the PDF workflow, for which he has raised an issue. Michael explained that a clause for terms and definitions was ultimately deemed unnecessary, leading to the streamlining of a few terms in the character-encoding area to avoid treatment as defined terms. Michael also highlighted extensive updates to the community repository's style guide, designed to align with Ecma standards and improve clarity by emphasizing direct sentences, active voice, and GitHub Markdown as the primary documentation dialect.
- **Website Updates and Documentation Maintenance Strategy**: Michael Herzog and John Horan updated the website to eliminate the reproduction of standard material, ensuring that pages now link directly to the approved PDFs and staging websites for ECMA-427 and VERS. For ongoing maintenance, Michael Herzog proposed maintaining markdown files for core narrative specifications (such as Clause 5 and Annexes B and C) within the purl-spec repository, with Michael Herzog and John Horan manually translating approved changes into the official Ecma spec.html file. Philippe Ombredanne questioned whether the `spec.html` could be entirely generated from markdown, but Michael Herzog explained that Ecmarkup is mandatory for standards, though they will raise issues to explore markdown converters. John Horan noted using Live Server in VSCode to display `spec.html` more readably, and Michael Herzog confirmed plans to proceed with the proposed markdown-to-`spec.html` workflow after finalizing the current cycle.
-  **Upcoming purl-spec Discussions and Major Changes**: Michael Herzog introduced several high-level discussion items created on the purl-spec side to handle major changes before altering the formal specification. Michael Herzog mentioned a discussion on merging PURL namespace and name components, a future discussion on removing encoded slashes '/', and a use case discussion regarding specifying the intended context or depth of a PURL in API calls rather than the PURL string itself. Philippe Ombredanne noted that full qualification levels often vary between detection and database references, validating the need to structure these discussions. Additionally, Michael Herzog and Philippe Ombredanne briefly mentioned a recent call regarding PURL registry design, with Michael Herzog planning to write up and share those details later.
- **Virtual PURL Type Proposal**: Michael Herzog brought up the active request for a "virtual" PURL type, noting that it features basic name, namespace, and version components intended to document unresolved or alternative dependencies, similar to C library virtual packages in Linux distributions or math libraries in Python ecosystems. Philippe Ombredanne explained the concrete use case from RPM, Debian, and conda/PyPI worlds, where multiple implementations can satisfy a single abstract dependency. While Philippe Ombredanne pointed out that virtual packages are practically difficult to resolve without centralized mapping to concrete PURL version ranges, Michael Herzog and Philippe Ombredanne agreed that adding the type causes no harm and can evolve, with Michael Herzog planning to provide feedback to Jaime Rodríguez-Guerra regarding namespace registration and potential interactions with SPDX and CycloneDX approaches.
- **Deprecation of golang PURL Type and Introduction of Go PURL Type**: Michael Herzog and Philippe Ombredanne discussed the long-standing issues surrounding the Golang PURL type, which suffers from structural mismatches with real-world module paths and build directories. Philippe Ombredanne advocated for deprecating the golang PURL type in favor of a new, greenfield "go" PURL type that reflects current Go module practices without forcing backward compatibility. Michael Herzog agreed with this strategic direction, proposing that the golang PURL type be placed on a deprecation schedule with test cases returning deprecation warnings, while directing future energy and new community proposals toward the new go PURL type.
- The meeting was adjourned.
